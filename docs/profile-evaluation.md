# Per-customer profile — evaluation

> ## ⚠ These numbers predate the 2026-09-25 model, and one of them got worse
>
> Every measurement on this page was produced against the bundle serving before
> **2026-09-25**, when the simulator was given a browser's frame clock and the
> model was retrained (`docs/evaluation.md`). This layer normalises its vectors
> with the served bundle's feature scaling, and that scaling moved — on
> identical raw telemetry, `scroll_hizi_varyansi`, `tereddut_skoru` and
> `ivme_degisimi` shifted by a mean of 0.18–0.20 on a 0–1 range. So this page
> is **stale**, and it is left standing rather than regenerated because
> regenerating it honestly requires re-deriving the constants first (below).
>
> `profile_lab.py` was re-run against the new bundle on 2026-09-25 (200
> identities, same seeds, same rules). Compared at the **same constants**
> `(8, 0.02, 3)` — the row in section 2 that both runs contain, so the model is
> the only thing that differs:
>
> - **mouse, a different person escalated: 47.9% → 18.4%.** This is the layer's
>   entire purpose — spotting an account takeover — and it lost more than half
>   of it.
> - mouse, same person falsely challenged: 5.0% → 3.8%.
> - keyboard, a different person escalated: 3.2% → 11.6%.
> - keyboard, abstained for want of a usable scale: 88.1% → 23.9%.
> - keyboard, same person falsely challenged: 0.3% → 3.2%.
>
> A plausible reading of the mouse row, **not** a measured one: the frame clock
> is a property of the machine, not of the hand, so it is shared between people
> on similar hardware. Several features now carry it, which compresses the
> between-person variance this layer works on. Confirming or refuting that
> needs a separate measurement that has not been run.
>
> The re-run also derives **different constants** than the ones `profiles.py`
> ships: `PROFILE_SCALE_FLOOR` 0.0062 → **0.02** and `PROFILE_TOP_K` 3 → **12**
> (`PROFILE_MIN_FEATURE_OBS` stays 8). Notably the 0.02 floor no longer causes
> the 88.1% keyboard abstention that the comment in `profiles.py` cites as the
> reason for lowering it — under the frame clock `zaman_kuantasyonu`'s
> within-person spread is larger, so the floor no longer excludes it.
>
> **Nothing was changed on the strength of this.** The constants were left
> where they are and this page was left as it was, because re-deriving a
> constant is a measure → set → re-measure loop, and changing three of them on
> the same afternoon as a model change, against synthetic identities, to move a
> rate, is the move this project's honesty rule exists to prevent. What that
> costs is stated plainly: the numbers below describe a bundle that is no
> longer served.
>
> **Prerequisite, not an improvement:** re-derive the constants and regenerate
> this page before `PROFILE_LAYER` is enabled anywhere that matters. The layer
> is off by default (`CLAUDE.md`, rule 8) and the shipped risk score does not
> depend on it, which is the only reason this is a follow-up rather than a
> blocker.


> **Sentetik kimlikler üzerinde ölçüldü; gerçek müşteri verisi yoktur.**
>
> Every number on this page was measured on **synthetic identities** generated by `train_model.simulate_identity_sessions()`, plus a sanity pass over **scripted Playwright browser runs** (`lab/real_telemetry.json`). **No real customer has been measured.** Every false-challenge rate is a **lower bound**: a synthetic person is a generator with fixed parameters, so their sessions are self-consistent in a way no real person is (device, posture, time of day, hurry, which hand holds the phone), and conformal calibration holds only while a person's sessions are exchangeable, which real drift breaks. The bias is in the direction that flatters the product.

Generated by `backend/profile_lab.py` on 2026-09-19 (200 identities, 20 fresh sessions each per modality, served bundle `model-sklearn1.8.0.pkl` read only, Python 3.13.2, numpy 2.3.3, runtime 1428 s). Re-run: `cd backend && python profile_lab.py` (under the backend lock).

What this layer is, so the numbers are read correctly: it can only turn `allow`/`warn` into `verify`. It never blocks, never approves, never changes a risk score. It is aimed at **human account takeover**; card-testing bots arrive without a customer reference and never reach it.

## 1. The assumption every number depends on

`WITHIN_IDENTITY_SD_RATIO = 0.6`: a person's session-to-session spread of each behavioural parameter is 0.6 of the spread between people. **Nobody has measured this**; it needs real customers. The between-person spreads in `train_model.IDENTITY_PARAMETERS` are assumptions of the same kind. Section 9 shows how the headline numbers move when the ratio moves. Touch is **not simulated at all** (the generator has no model of a finger), so nothing below says anything about phones.

## 3. `PROFILE_MIN_FEATURE_OBS` — how many observations a median/MAD needs

For each (identity, modality, feature) with a non-zero spread, the 'true' centre and scale are taken from all of that identity's sessions (up to 70); then 60 random subsets of n sessions re-estimate them. Cells are the median, over identity x feature, of the RMS error in units of the true scale. The subsets come from the same pool as the 'truth', so the error at large n is slightly understated (finite-population effect).

## 5. Same person vs a different person (the account-takeover case)

Measured constants, alpha 0.05, a mature profile of 20 sessions per identity and modality. **Same person**: 20 fresh sessions of the identity that owns the profile — a legitimate returning customer, so every escalation is a **false challenge**. **Different person**: 20 sessions of 20 other identities on the same modality (the grandchild holding grandmother's phone, or an account-takeover attacker) — here an escalation is the extra verification the layer exists to ask for. Rates are over **all** sessions presented; abstentions (thin session, too few participating features) count as no challenge. Intervals are 95% cluster bootstrap over identities.

| modality | same person: false challenge | same person: abstained | different person: escalated | different person: abstained | AUC of p-value (evaluated only) |
|---|---|---|---|---|---|
| mouse | 4.9% (4.0%–5.9%) | 0.0% | 47.5% (44.0%–50.8%) | 0.0% | 0.841 |
| keyboard | 3.8% (3.0%–4.7%) | 19.6% | 26.4% (23.3%–29.6%) | 19.7% | 0.735 |

> **Sentetik kimlikler üzerinde ölçüldü; gerçek müşteri verisi yoktur.** Every false-challenge figure is a **lower bound**: a synthetic identity is more self-consistent than any real person, so real customers will be challenged more often.

Why the same-person rate is not zero: with 20 references the smallest p-value is 1/21, so a session is challenged exactly when its deviation exceeds that of all 20 of the customer's own past sessions, each of them scored against the other 20 points (full conformal). For exchangeable sessions that happens at most 1 time in 21 (4.8%) of the sessions the layer evaluates (1 in 20 when one reference cannot be scored), which is the floor on the cost of this layer for a customer as consistent as a synthetic one.

**Calibration check.** The shipped rank (`profiles.evaluate_profile`) is full conformal: the candidate and every reference are scored by one function, each against the other 20 of the 21 points on its own participating features, which makes the rank exact under exchangeability. ## 7. Poisoning: attacker vectors in the victim's buffer

Mouse profiles, alpha 0.05. The attacker is one fixed other identity per victim. After `k` of the attacker's sessions have been learned into the victim's buffer, the attacker's fresh sessions and the victim's own fresh sessions are presented. How a learned session is stored decides what it does, so there are two tables. **Stored on probation** is the shipped rule for a session learned only because a passed step-up rescued a profile challenge, i.e. the attacker holding a phished code: the buffer is built through `profiles.admit_vector` and the reference set is read back by the rule `main._read_profile_context` uses, under which a probation vector is not a reference (at most `PROFILE_PROBATION_MAX = 4` are stored per profile and input type, beside the 20 references and never evicting one). **Promoted to a reference** is what such a vector becomes when the merchant settles the payment (`POST /api/outcome`), and what every probation vector was before probation vectors were excluded: the `k` oldest victim references give way to `k` attacker references. A self-healing rebuild (`PROFILE_HEAL_AFTER = 3` passed challenges in a row) also promotes, but cuts the profile to `PROFILE_HEAL_KEEP = 10` references, below maturity, so the layer then abstains on that profile instead of ranking against the second table.

**Stored on probation, the curve is flat.** The attacker's sessions were escalated 47.5% of the time with none of his sessions stored and 47.5% with 6 learned (4 kept, the storage cap), because every victim's reference set came back identical to the one with none: a passed step-up no longer buys the attacker anything inside the statistic. **Promoted, it is not flat:** one attacker reference took the attacker's escalation rate from 47.5% to 25.5%, and 4 to 13.7%. The mechanism is the rank itself: at alpha 0.05 with 20 references a session is challenged only when its deviation exceeds the deviation of **every** reference (each scored against the other points), so one reference that is itself far from the customer's centre, the attacker's learned session, shields every later session less extreme than it. "One absorbed vector moves the p-value by at most 1/(n+1)" is true, and 1/(n+1) is exactly the step between challenged and not. That is why a probation vector is not a reference, and why promotion asks for what one phished code does not give: the merchant's statement that the payment was legitimate, or 3 passed challenges in a row. What passing still buys lies outside the statistic and is not measured here: each passed challenge spends one of the profile's `PROFILE_MAX_ESCALATIONS = 3` per 30 days (a challenge nobody answers spends nothing), and 3 passed in a row rebuild the profile below maturity, after which the layer says nothing on it until it matures again. Against an attacker who can pass the merchant's step-up at will, this layer's strength is that channel's.

**Rescued, then returning** (the grandchild's side of the same rule). For every mature profile one fixed other identity plays the grandchild and presents its 20 fresh sessions in order; every consecutive pair whose first session was challenged counts once. The first session is stored as rescued (a passed step-up), the second is ranked against the reference set read back from that buffer: under the shipped rule, and under the old one in which the rescued session replaced the victim's oldest reference. Alpha 0.05, 20 references; intervals are cluster bootstrap over profiles.

| input type | grandchild sessions challenged | challenged sessions followed by another | returning session challenged again (shipped: rescued session on probation) | same sessions, rescued session counted as a reference (old rule) |
|---|---|---|---|---|
| mouse | 47.5% (42.9%–52.4%) | 1799 | 71.7% (67.1%–75.9%) | 34.9% (32.2%–37.5%) |
| keyboard | 25.4% (21.0%–30.0%) | 966 | 62.4% (55.3%–68.8%) | 30.4% (26.3%–34.1%) |

> **Sentetik kimlikler üzerinde ölçüldü; gerçek müşteri verisi yoktur.** Every false-challenge figure is a **lower bound**: a synthetic identity is more self-consistent than any real person, so real customers will be challenged more often.

**The accepted cost, measured.** The grandchild's rescued session is not a reference either, because the statistic cannot tell it from the attacker's. When a different person was challenged, passed step-up and came back in the same pattern, the next session was challenged again 71.7% of the time on mouse and 62.4% on keyboard; under the old rule, in which the rescued session counted as a reference, the same sessions were challenged again 34.9% and 30.4% of the time. Each of those challenges is one more verification, never a block, until the merchant settles the earlier payment or 3 passed challenges in a row promote the pattern; and once 3 challenges have been passed in 30 days, the profile asks for no more in that window.

## 12. The measurement that is still missing (spec §10.3)

The browser lab cannot produce one person across twenty sessions and three device classes, so **no threshold on this page is validated**.
